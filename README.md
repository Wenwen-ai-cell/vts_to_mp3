# vts_to_mp3

把 **Vivo / iQOO 手机录屏**生成的 `.vts` 文件批量转换成 MP3。

纯 Python 单文件工具，**不需要 ffmpeg、不需要联网**，能救回开头损坏、普通工具打不开的 `.vts`。

```
双击 启动转换工具.bat  ->  浏览器里选文件夹 -> 扫描 -> 开始转换
```

---

## 一、这些 `.vts` 到底是什么

不是 DVD 的 `VIDEO_TS`，而是 **伪装成 `.vts` 的 MP4/M4A 容器**。解剖一个真实文件的结果：

| 组成 | 说明 |
|---|---|
| 一条 AAC 音轨 | 48 kHz，`mp4a`；元数据里写着 `Lavf58.12.100`（FFmpeg） |
| 一张封面图 | `udta → meta → ilst → covr` 里的 JPEG（常见 720×720） |
| 标题 / 专辑 | 例如「视频转歌_xxx」 |

**很多文件的开头被覆盖过**（实测有一个是前 128 KiB 变成随机字节），
连 `ftyp` 结构头都没了。后果是：

1. 播放器和常规转换工具**直接拒绝打开**；
2. 就算强行把容器头补好，解码器遇到那段垃圾数据后会**放弃整条流** ——
   实测输出是「第 1 秒削顶噪声 + 第 2~36 秒全静音」。

所以「修文件头」这条路是死的，必须**绕开损坏部分重建**。

---

## 二、工具怎么做的

```
解析残留的 moov
   -> 逐个取出 AAC 帧
   -> 用首字节特征剔除损坏帧
   -> 重新封装成标准 M4A
   -> 交给 Windows Media Foundation 解码并编码成 MP3
   -> 写入 ID3（标题 / 专辑 / 封面）
```

### 判断哪些帧是好的

同一台设备产出的合法 AAC 帧，**首字节几乎总是同一个值**（本例 `0x01`，
完好文件里占 99.9%，而被覆盖的区域是随机字节、命中率只有 ~0.4%）。

工具统计出「主导首字节」，把**连续 ≥3 帧**不符合的区间判定为损坏区，
取最长的一段完好区间来转换。容忍少量零散异常帧，避免误伤本来正常的文件。

### 试过但行不通的两条路

| 方案 | 结果 |
|---|---|
| 补 `ftyp`/`mdat` 头直接转 | `CanTranscode: True`，但输出是**噪声 + 全静音** |
| 抽成 ADTS 裸流再转 | prepare 说可以，实际转码 40 秒输出 **0 字节**，卡死 |

## 三、用法

### 网页界面（推荐）

双击 **`启动转换工具.bat`**，浏览器自动打开 `http://127.0.0.1:8756/`。

1. 填「要转换的文件夹」→ 点 **扫描**
2. 表格会显示每个文件**丢了多少开头**、能转出多长、有没有封面
3. 如果原始录屏还在，填上「原始录屏所在文件夹」，可以**把开头那几秒补回来**
4. 点 **开始转换**

### 命令行

```bat
python vts2mp3.py --cli D:\录像\vts
python vts2mp3.py --cli D:\录像\vts -o D:\输出 --bitrate 320
python vts2mp3.py --cli D:\录像\vts --src C:\Users\me\Downloads
```

也可以把文件夹**直接拖到 `启动转换工具.bat` 上**，等于跑一次命令行转换。

| 参数 | 说明 |
|---|---|
| `-o, --output` | 输出目录（默认 `<输入目录>\mp3`） |
| `--src` | 原始录屏目录，可给多个，用于补回损坏开头 |
| `--bitrate` | MP3 比特率 kbps，默认 256 |
| `--port` | 网页端口，默认自动挑 |
| `--tmpdir` | 临时目录，默认自动挑 |
| `-v` | 出错时打印完整堆栈 |

## 四、关于「用源录像补回开头」

原始录屏（`Screenrecording_20261016_190100.mp4`）和 `.vts`
（`Screenrecording_20261016_1901001792148550258.vts`）名字是**前缀关系**，
工具按这个关系在 `.vts` 同目录和 `--src` 目录里找候选。

**不会盲信文件名**：必须在「完好区间」内逐帧比对完全一致才会采用，
否则跳过并打印原因（长度不足 / 内容不一致 / 与 .vts 完全相同）。

| 场景 | 结果 |
|---|---|
| 找不到源录像 | 转出 30.5 秒（丢掉被覆盖的前 6.7 秒） |
| 找到源录像 | 转出完整的 37.3 秒 |

---

## 五、实测数据

对一个开头损坏 6.7 秒的 `.vts`：

| | 无源录像 | 用源录像补回 |
|---|---|---|
| 时长 | 30.49 s | 37.21 s |
| 静音秒数 | 0 | 0 |
| RMS 范围 | 497 ~ 2088 | 531 ~ 2041 |
| 输出大小 | 1.0 MB（含 299 KB 封面） | 1.17 MB（含封面） |

把生成的 MP3 解回 PCM 与源音频比对，**相关系数 0.99833**，逐秒 0.995~0.999，
差异仅来自 MP3 有损压缩。

## 六、依赖

- **Windows 10 / 11** —— 转码用系统自带的 Media Foundation（WinRT）
- **Python 3.7+** —— 只用标准库，**不需要 pip 安装任何东西**
- 转码引擎通过 `powershell.exe`（Windows PowerShell 5.1）调用，系统自带

> 为什么不用 ffmpeg？Media Foundation 一样能解码 AAC、编码 MP3，而且零依赖。

## 八、已知限制

- 只处理**音频轨**；如果 `.vts` 里存的是视频，不会转出视频
- 损坏区如果落在中间，只会取最长的那段完好区间，前后内容拿不回来
- 找不到源录像时，被覆盖的开头无法重建（数据本身已丢失，不是算法问题）
- 仅 Windows 可用
